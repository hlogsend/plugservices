# Code-level audit — 2026-09-10

Scope: this repository only. **Production was not reachable from this session**
(org egress policy returned HTTP 403 on CONNECT for `plugservices.ca`,
`tickets.plugservices.ca` and `api.netlify.com`; recorded in the proxy's own
`recentRelayFailures`). Nothing below was verified against the live site.
Every claim is traceable to a file and line in this repo.

## 0. What this repo is — and why it constrains everything

`public/` is a **CDN capture**, not deploy source (see BACKUP-STATUS.md), and
it is now also **stale**:

| measurement | value | source |
|---|---|---|
| `public/site.js` size | 101,042 B | `wc -c` |
| `public/site.js` sha1 | `37f9c580e845b8ba42cdae1ab54c3244d92ef19f` | matches BACKUP-STATUS.md |
| version guards present | v70, v71, v72, v73 | `grep __plugV` |
| live `/site.js` on 2026-08-24 | 107,274 B | `_redirects.OBSERVED` probe |
| live `site.js` after v77 | 125,970 B | project version ledger |

The repo is **~25 KB and four append-versions (v74–v77) behind production.**

Consequence, and it is the governing fact of this audit: **no file in `public/`
may be edited as a fix.** An edit here is an edit to a stale copy; deploying it
would roll production back through v74–v77. Production is maintained by
*appending* guarded `plug-append-vNN.js` payloads, and the deploy procedure
requires reading the current live `site.js` sha1 first — which this session
cannot do. Authoring a v78 blind would risk exactly the last-writer-wins
inline-style race the project has already been burned by twice (v74c, v74e).
**No JavaScript was therefore written.** That is a deliberate refusal, not an
omission.

## 1. Reported "P0 #1" — homepage claims no events while showing events

**Not reproducible in code. Assessed as a false positive.**

The strings exist in the static HTML, but both are `style="display:none"` and
`site.js` never reveals them:

- `public/site.js:605` — `const sn=document.getElementById("sampleNote"); if(sn) sn.style.display="none";`
  runs unconditionally on **every** `applyFilters()` pass. The sample note can
  never be shown.
- `public/site.js:589` — `EVENTS.filter(e=>!e.sample && matchFilter(e))`. Sample
  records are excluded from the rendered list entirely.
- `public/site.js:545-549` — `renderEmptyState()` begins
  `if(shownCount){ host.style.display="none"; host.innerHTML=""; return; }`.
  The empty-state block is cleared whenever one or more cards render.

The code is commented `v57: HONEST EMPTY STATE (no fake listings, ever)` — this
was fixed at v57, before the version in this repo. The reported symptom is what
you see reading **page source or a text scrape**, where `display:none` content
is still present in the markup. It is not what a browser renders.

Residual uncertainty: v74–v77 are not in this repo. Their documented subject
matter is contrast, tap targets, past-ticket hiding and the footer/header
wordmark — none touches empty state. Confidence high; **not** verified live.

## 3. NEW — HIGHEST SEVERITY: guest portal has no authentication

`public/portal-guest.html:251-256`

```js
var r=await fetch(API+"/portal/guest",{method:"POST",
  headers:{"Content-Type":"application/json"},
  body:JSON.stringify({email:document.getElementById("gm").value})});
var d=await r.json();
if(d && (d.tickets||[]).length + (d.orders||[]).length > 0){D=d;show();}
```

An **email address alone** is sent, and the response body carries the tickets
and orders, which are rendered immediately — including the QR code, generated
client-side at line 293 as `"PLUGSVC:"+code` from `t.code || t.ticket_no`.

There is no token, no magic link, no one-time code, no session. The page states
the design intent outright at line 227: *"Prefer a password? A full account
option is coming soon — for now, your email is your key."*

Impact, in order of severity:

1. **Ticket theft / gate bypass.** Anyone who knows an attendee's email address
   can retrieve that attendee's ticket code and render a scannable QR. For a
   paid event this is unpaid entry, and the loss lands on the organizer.
2. **PII disclosure.** Name, email, full order history and totals are returned
   to an unauthenticated caller.
3. **Email enumeration.** Line 255 shows the error state *only* when zero
   tickets are found, so the response distinguishes "no such customer" from
   "customer exists" — the exact pattern the audit's own §17 and §103 say to
   avoid.

This outranks both reported P0s. A wrong total is a trust and conversion
problem; this is a financial-loss and privacy-breach problem.

**Caveat:** the enforcement lives server-side in
`/wp-json/plug/v1/portal/guest`, which was not reachable and whose source is not
in this repo. What is proven is the **client contract**: the request carries no
credential and the response carries ticket data. Confirm against the bridge
before remediation, but the client side alone is sufficient grounds to treat
this as urgent.

By contrast the **organizer portal is materially better** — every privileged
call (`/portal/organizer`, `/portal/event`, `/portal/update-event`,
`/portal/delete-event`, `/portal/payments`, `/portal/checkin`) uses
`credentials:"include"` against a real WordPress cookie session. Server-side
object-ownership checks (IDOR) still need review at the bridge, which this
session could not read.

## 4. NEW — organizer registration was a dead loop on organizer.plugservices.ca

`public/portal-organizer.html:~236` links to `href="/organizer-register"`
(host-relative). The OBSERVED probe proved `organizer.plugservices.ca` runs a
**forced catch-all**: 9 of 9 probed paths, including `/zzz-does-not-exist`,
returned `portal-organizer.html` at 48,841 bytes. The only proven exception was
`/register`.

So on the organizer subdomain, *"Register now — it's free →"* returned the
**sign-in page**, not the registration form. That is a dead loop at the top of
the organizer acquisition funnel — the funnel described as the strongest asset
in the product review.

**Fixed** in `_redirects.RECONCILED` by routing both `/organizer-register` and
`/register` on that host, plus `/organizer-login` explicitly (it previously
resolved correctly only by accident, via the catch-all).

## 5. NEW — event pages emit no structured data

`grep '"@type": "Event"'` matches **one file: `public/index.html`**, carrying 4
hardcoded events. `site.js` emits **no JSON-LD at all** — zero matches for
`application/ld+json`.

Every dynamically rendered event page (`/event.html`) and all seven city pages
therefore ship **no Event schema**. Google cannot read prices, dates, venues or
availability for the marketplace. The audit's SEO sections assume this exists;
it does not. This is the single largest cheap SEO win available, and it belongs
in a `plug-append-v78` payload once a live sha1 can be read.

## 6. NEW — "QR check-in" is not implemented on this side

No scanner exists anywhere in the repo: zero matches for `jsQR`,
`html5-qrcode`, `getUserMedia`, `BarcodeDetector` or `qr-scanner`. The only QR
library present is `qrcodejs` in the guest portal, which **generates** codes.

Check-in in `portal-organizer.html:438-443` is a per-row `Check in` **button**
that POSTs an attendee id — a manual list check-off, not a scan. The organizer
marketing copy promises *"QR code emailed the moment you pay — scanned at the
door."* If a scanner exists it is on the WordPress side; from the static site,
the promise is not backed by an implementation here.

Related, minor: `downloadGuests()` (line 550-557) is labelled *"Download guest
list (Excel)"* but emits **CSV** (`text/csv`, `.csv`). It builds the file
client-side from data the dashboard already loaded, so it opens no new
authorization surface beyond the dashboard itself.

## 7. `netlify/functions/submission-created.js` — reviewed, no defects found

The rebuilt handler is sound for its purpose. Notable and correct decisions:

- Always returns 200, with the reasoning documented in-file: a non-2xx makes
  Netlify retry, which would **double-publish** an event that actually
  succeeded. Correct.
- Credentials come from `process.env` only; nothing is hardcoded.
- `asUrl()` rejects anything that is not `http(s)://` before forwarding.
- It forwards `time_zone` even though the current bridge ignores it, so the
  field starts working the day the bridge reads it, with no redeploy.

One standing risk, from the project ledger rather than this file: a Netlify
deploy body that omits the `functions` key **deletes the site's functions**, and
this has already silently dropped every organizer submission for a period. Any
deploy must carry `functions`.
